## Two C# paths: native (bflat) and managed (RustCLR)

C# runs two ways, side by side. **Native**: bflat/NativeAOT `--stdlib:zero` + the `bzstart.rs` shim (the apps below; machine code, fast, but no garbage collector -- see "Freestanding C# apps have no GC"). **Managed** (2026-11-02, increment 1): **RustCLR**, the runtime of RustNetRuntime (`github.com/DotNetVibeCoderz/Vibe_Runtime`, our own re-implementation of CoreCLR in Rust), as an ordinary ring-3 program `/disk/CLRHOST.ELF` that runs a plain `dotnet build` assembly unmodified: `CLRHOST.ELF <path.dll> [args]` (kernel: `clr::run(dll, args)` = `app::spawn_with_args(clr::HOST, ...)` + `app::wait`). It has a tracing mark-sweep GC and RustBCL (generics, LINQ, lambdas/delegates, exceptions, strings, collections, reflection, Regex, decimal, ...), so everything the native path cannot do works; it is an interpreter (slower), and the **same .dll runs on x86-64, ARM64 and RISC-V** -- the way C# reaches RISC-V, where bflat has no target. **Host** (`userland/clrhost`, its own cargo workspace + `rust-toolchain.toml`, built by `scripts/build-clrhost.*` for `x86_64-unknown-none`, `aarch64-unknown-none` and `riscv64imac-unknown-none-elf` into `userland/clrhost/target/<target>/release/clrhost`; bzimage packs the matching one as `/disk/CLRHOST.ELF` into each image -- `clrhost_elf()` in build.rs; CI's build job runs the script): depends on `rustclr-core`/`-gc`/`-metadata`/`-bcl` (`default-features = false`, bcl feature `libm-math`) as **git dependencies pinned to a commit** (bump `rev` in Cargo.toml to take a newer RustCLR); `sys.rs` = raw syscalls per arch (the x86 clobber rules of `bzstart.rs` apply), `heap.rs` = `linked_list_allocator` over 768 MiB reserved with `MMAP(PROT_NONE)` and committed in 8 MiB `MPROTECT` steps (frees are reused), a 16 MiB committed interpreter stack (`run_on_stack`; the kernel gives 128 KiB and does not grow stacks), `BzHost` implements RustCLR's `Host` (DEBUG_WRITE console, TICKS/CLOCK_RTC clocks, PROC_ARGS), and the host re-registers `System.Reflection.Assembly::Load/LoadFrom` (RustBCL's `no_std` build has none: already-loaded assemblies first, then `/disk/<FIRST8>.DLL` or the given path). Link: `link.ld` at 0x400000, `relocation-model=static` (`.cargo/config.toml`); **x86-64 keeps the target's "kernel" code model** -- its precompiled core/alloc use it and LTO refuses a mix (`code-model=small` -> "failed to load bitcode"). ELF sizes ~1.5-1.9 MB with the full BCL. **Apps** (`userland/clr-apps/<Project>/`, built by `scripts/build-clr-apps.*` -> `userland/clr-apps/dist/<8.3>.DLL`, **committed** so images build without the .NET SDK; `.gitignore` ignores only the root `/dist/`): `HELLOCLR.DLL` (9 checks, each something zerolib cannot do: static reference field, `object[]` stores, string interpolation/concat, interfaces, LINQ + lambdas, GroupBy/Dictionary, try/catch/finally, a GC that reclaims ~40k objects while keeping a live chain, args) and RustCLR's own `MODERN.DLL` (ModernSyntax fixture, `checks=35 failures=0`). `clr::boot_demo(arch)` (pc_main after `multiproc_demo`, arm_main/riscv_main after `run_boot_programs`) -> `MILESTONE: CLR OK` + the program's own `checks=35 failures=0`; smoke requires both on IDE, arm64 and riscv64. **Identical counters on all three architectures** (HelloClr: 560,932 IL instructions, 40,133 calls, 39,980 objects freed in 1 collection). **Increment 2 (real threads, 2026-11-02):** RustCLR only had threads with `std` (`Thread.Start` ran inline without it, so Conformance's producer/consumer waits never returned and hung the boot). Fixed **in RustCLR** (Vibe_Runtime `main` 6e31a5a, merged + pushed with the user's approval; `clrhost` pins it): a new crate **`rustclr-thread`** provides the slice of `std::{sync, thread, time}` RustCLR uses (`Mutex`/`MutexGuard`/`Condvar`/`Arc`, `thread::spawn/Builder/current/sleep/yield_now/available_parallelism/JoinHandle`, `Instant`) -- re-exports with `std`, otherwise built on `Hooks` the embedder installs (`spawn`, `join`, `wait(word, expected, timeout_ns)`, `wake`, `now_ns`, `current_id`, `yield_now`, `parallelism`); `rustclr-gc`/`-core`/`-bcl` got a **`threads` feature** (implied by `std`) that the shared heap, safe points, statics, monitors, task pool, Thread/Task/Parallel/timers are gated on instead of `std`; the `core` prelude's `Arc` is the real one with `threads` (an `Rc` only on MCUs); `rustclr-sched` builds its lock-free queue without `std`. ## Debugger + profiler (v1.0)

**Debugger:** `scripts/debug-kernel.ps1`/`.sh` boot QEMU **paused** with a GDB stub on `tcp:1234` and attach GDB against the un-stripped kernel ELF (`kernel/target/x86_64-unknown-none/release/bzkernel`), sourcing `scripts/debug-kernel.gdb` (helpers `bz-break-main`, `bz-faults`, `bz-regs`). Rust symbols are mangled but GDB demangles them, so `break kernel_main` works. If `gdb` isn't on PATH the script still starts QEMU and prints the manual attach commands. The manual path is still `QEMU_EXTRA="-s -S"` + `target remote :1234`.

**Profiler:** `profile.rs` is an instrumented TSC zone profiler — `profile::Guard::new("name")` times a scope to its `Drop` and accumulates cycles per name. It is **inert unless `profile::enable()` was called** (one atomic load when off), so instrumentation left in the tree never perturbs boot timing — do not profile-enable during normal boot. Hot paths already carry zones (`syscall` in `dispatch_from_user`, `wm::compose` + `fb::present` in `present_now`). Shell command `prof [self|on|off|reset|report]`; the report goes to serial. `profiler_demo()` in `main.rs` verifies it deterministically (nested zones, 20× cost ratio, exact call counts, disabled-work-absent) → `MILESTONE: PROFILER OK`. It measures **inclusive** scope time; split child work into its own zone for self-time (that's why compose/present are separate). Full guide: `docs/debugging.md`.

## Syscall pointers from ring 3 are untrusted (v1.0 hardening)

Every pointer argument arriving from ring 3 is validated before the kernel touches it. `memory::validate_user_range(ptr, len, need_write)` requires the range not to wrap, to sit entirely below `USER_ADDR_MAX` (0x8000_0000 — every kernel mapping, including the heap at 0x4444_4444_0000, is above it), and **every page in it to be present and `USER_ACCESSIBLE`** (plus writable for output buffers). `validate_user_cstr` does the same for NUL-terminated paths, re-checking at each page boundary. Both are wired into every pointer-taking syscall.

**What this closed:** an unprivileged app could previously pass a *kernel* address and have the kernel read it back out through `DEBUG_WRITE` (information leak) or **write syscall results into kernel memory** through `SYS_STAT`/`PROC_LIST`/`PKG_LIST`/`FS_READ`/`NET_RECV` — an arbitrary kernel write, i.e. full privilege escalation. An unmapped pointer was fatal a different way: the kernel page-faulted inside the syscall and died. The old `sys_win_create`/`sys_debug_write` TODOs ("full address-space validation arrives with multi-process isolation") are now honoured.

**Important:** validation applies only on the ring-3 path. `usermode::syscall_dispatch_c` calls `syscall::dispatch_from_user`, which sets a flag the validators consult; kernel-internal callers of `dispatch` (boot self-tests, the shell) legitimately pass their own addresses and stay trusted. Getting this wrong is immediately obvious — the kernel's own `syscall_smoke_test` passes a `&str` in kernel rodata to `DEBUG_WRITE`, so an unconditional check panics the boot at `main.rs`'s `assert_eq!(written, msg.len())`. Verified headlessly by `syscall::security_self_test()`, which fires 14 hostile probes (kernel addresses, unmapped pages, ranges overflowing the user half, wrapping lengths, null) and requires every one to be refused with `INVAL` → `MILESTONE: SECURITY OK`.

**ABI v1 is frozen.** `abi_v1_is_frozen` (Rust) and `AbiV1IsFrozen` (C#) pin `ABI_VERSION`, `COUNT`, the size *and* alignment of all ten boundary structs, and the error codes, so a renumbering or field-width change fails in tests before it can reach a released image. Adding a syscall = append + bump `COUNT` + extend both tests; changing an existing one = a new ABI major version.

**Kernel gotcha (hard-won): the privilege/SYSCALL stack must be large (64 KiB, `gdt.rs` `PRIV_STACK_SIZE`).** `PRIVILEGE_STACK` doubles as the TSS rsp0 interrupt stack **and** the SYSCALL kernel stack for a non-threaded app's main thread (`usermode.rs` sets `SYSCALL_KSTACK_TOP` to its top). The deepest thing that runs on it is a `WIN_PRESENT` syscall → `wm::present_now` → `compose_into`, which composites every open window (title bars, Noto text, canvas blits) — with ~20 windows open after the boot demos, the old 20 KiB (`4096*5`) overflowed into adjacent statics **intermittently** (depending on binary layout), smashing return addresses → a breakpoint/#PF/#DF cascade + rodata dump on serial. This looked exactly like the `from_raw_parts`-over-user Heisenbug but was a *different* latent bug (a too-small stack), and it re-triggered whenever a change shifted the layout (e.g. adding the interactive apps). If you see that cascade again, suspect a kernel stack overflow, not just user-memory slices. Relatedly, `wm::present_now` composites into a **reused static `PRESENT_BUF`** (not a fresh 3.7 MiB `Vec` each call) so repeated presents from an interactive app don't fragment/exhaust the heap, and the kernel heap is **32 MiB** (the desktop's back buffer + `PRESENT_BUF` + ~20 window canvases + RAM disks crossed 16 MiB). Suite apps live on `/disk`, so their milestones only appear on the IDE boot medium (the kernel's ATA-PIO driver can't read `/disk` on ahci/nvme/usb) — put app-side markers in the IDE-only smoke list, kernel-side ones (`SUITE OK`) in the shared list. **Kernel gotcha (cost a nasty Heisenbug):** never build a `&[u8]`/`&[u32]` slice with `from_raw_parts`/`from_raw_parts_mut` over a *user-space* buffer — the optimizer then assumes the whole region is dereferenceable/immutable and it corrupted the boot (scrambled serial/rodata dump, page/double faults). This is **layout-sensitive**: it stayed latent for many builds and re-triggered the instant a new kernel function (`panen_suite_demo`, added for the app suite) shifted the binary. The robust fix (`syscall.rs`): a `copy_user_bytes` helper reads the user buffer **per element with `read_volatile`** into a kernel `Vec`, and every string syscall (`DEBUG_WRITE`, `WIN_CREATE`, `WIN_CMD` `DRAW_TEXT`) now works from that copy; `PROC_LIST` writes results out with `write_volatile` instead of a `&mut` slice; the `BLIT` path already read per-pixel with `read_volatile` and passes a raw pointer. Do not reintroduce a slice over user memory in a syscall. Investigation confirmed the path: bflat's `--stdlib:dotnet` provides the real BCL + GC (`libRuntime.WorkstationGC.a`), gated behind a ~200-symbol glibc/pthread/Linux-syscall PAL + threads; next increments build the rest of the PAL (sync/futex/TLS/time/stdio → link the runtime → real LINQ/Regex/Tasks). Also: C# `[UnmanagedCallersOnly]` function pointers don't resolve correctly under bflat zerolib yet (thread entries use a shim-provided native worker for now). Still missing: **the rest of the .NET PAL (sync/TLS/GC init) + thread pool + full V8/CPython engines + ring-3 native polyglot runtime** (needs CoreCLR/GC), **native VMX/SVM driver (VMXON/EPT/VMCB)** + nested HW virt (not exposed under QEMU/TCG), production LLM (GGUF/GPU) + inference scheduler + CV/GenAI audio-video, real GPU driver, APIC, NVMe/AHCI/USB + e1000 drivers, journaled FS, TCP/UDP, tiling WM, full HTML/CSS/JS engine, ACPI S3, **CoreCLR/JIT + GC + reflection** (apps are freestanding zerolib/NativeAOT, no heap — see below).

## Boot modes: normal (fast) and self-test (2026-11-04)

**A normal boot goes straight to the desktop; every demo, test program, self-test and milestone runs only on the self-test boot.** `bootmode.rs` decides it once, early: QEMU's fw_cfg file **`opt/buitenzorg/selftest`** (`-fw_cfg name=opt/buitenzorg/selftest,string=1`; I/O ports 0x510/0x511 in `arch/x86/fwcfg.rs` on PCs -- checked first thing in `kernel_main`, it needs nothing else; the `qemu,fw-cfg-mmio` device from the DTB on ARM64/RISC-V `virt`) or **`bz.selftest`** in the DTB's `/chosen/bootargs` (the Pi's direct boot: QEMU `-append`, or `cmdline.txt` on a board). Real hardware therefore always boots normally. **Every smoke step and `bench.sh` pass the switch** (`$selftest` / `selftest=(...)` in both smoke scripts, `-append bz.selftest` for raspi4b) -- a new QEMU invocation in a test script must add it too, or its milestones never appear. `scripts/run-qemu.ps1 -SelfTest` boots the self-test way by hand. **x86** (`pc_main.rs`): `fast_boot()` = the init the desktop needs in the self-test boot's order (task init, PCI, IDE/virtio-blk, virtio input/GPU, PS/2 mouse, /disk + /ram, region config, icons, loopback net, address spaces, SMP, I/O APIC, packages, WM, theme) then `desktop::run()`; **ARM64/RISC-V** keep one flow with every test gated on `st` / `bootmode::selftest()` (storage mounts but skips its write test, the timer starts without the 50-tick check, the GPU comes up without its test frame, secondary CPUs start without the 200 ms check, `shared_kernel_setup` skips security/gfx3d/network tests and returns before USB/NICs). The second half runs behind the desktop in **`boot_background`** (wallpaper, sound, USB, NICs incl. DHCP and the Pi's Ethernet + SNTP, RNG seed file, accounts), spawned with **`task::spawn_unlocked`** and yielding between steps: a kernel task holds the BKL while it runs, and the first desktop frame waited ~3.5 s for it when it did; without yields the compose helper on the other CPU could not run. A normal boot keeps the log on serial (`interactive::set_active()` before the logo -- drawing/scrolling the console on the framebuffer cost time) and shows no splash. The x86 LAPIC timer is calibrated over 1 PIT period on a normal boot (3 on the self-test boot, whose timer checks want that precision). `desktop::run` prints **`[boot] first desktop frame on screen N ms after kernel start (M ms after power-on ...)`** from the CPU counter (`boot::mark_kernel_start` / `elapsed_ms`; the counter runs from power-on, so M includes firmware + loader). Measured under QEMU TCG (wall, QEMU start -> first desktop frame): **x86 ~4.4-5.2 s, ARM64 ~6.8 s, RISC-V ~9.1 s**, of which the kernel is ~0.14 s / ~0.12 s / ~0.24 s -- the rest is emulated firmware (SeaBIOS / edk2) and the loader (the old boot took 3+ minutes to READY). `[boot] phases (ms): ...` (`boot::phase(name)` marks, printed with the first frame; 24 slots, no allocation) shows where the kernel's time goes. ## Ring-3 apps must re-enable interrupts on exit (do not regress)

`usermode::enter_user` calls `x86_64::instructions::interrupts::enable()` after the app returns. The EXIT syscall's entry clears IF (SFMASK) and its longjmp return path (`return_to_kernel`) never restores it, so without this the kernel runs with interrupts disabled after any ring-3 app exits — the timer stops, and `desktop_loop`'s `hlt` halts forever (this silently broke the interactive desktop/screensaver/animations from v0.4 until v0.11, since only static screenshots were checked).

## Freestanding C# apps have no GC (important for app authors)

Ring-3 C# apps compile with bflat `--stdlib:zero` (zerolib) + the `bzstart.rs` shim. **As of v0.15 increment 4, heap allocation works**: `SystemNative_Malloc` is now a growable, zeroed mmap-backed bump heap, and zerolib's `new`/`RhpNewArray` route through it — so **`new`, arrays, heap objects, and generics work** (verified by `heap.cs`). The remaining hard limits are all rooted in **uninitialized GC statics**: (a) a `static` field holding a reference reads garbage (XOX first hit this: a `static readonly char[] _board = new char[9]` faulted at a wild address) — keep heap state in **locals**, not `static` refs; (b) a **method-group→delegate** conversion caches the delegate in a GC static and faults — use **function pointers** (`delegate*<int,bool>` + `&Method`) instead (hit in `bcl.cs`); (c) storing a reference into an **object-array element** (`_arr[i] = obj`) emits `stelem.ref`→`RhpStelemRef`, whose array-covariance check faults — store references into **object fields** instead (a **linked list** of nodes works, `RhpAssignRef` is fine), which is why `Buitenzorg.UI`'s `UIElement` keeps children as a linked list, not `object[]` (hit building the UI toolkit in v0.16). There's also no reclaiming GC yet (bump-only — memory is freed only when the app exits). Full GC + static-ref init arrives with the NativeAOT `--stdlib:dotnet` link. More v0.9-era gotchas along the same theme (still apply for the freestanding string path): (1) `stackalloc T[n]` of a **struct** array emits a checked size multiply needing `ThrowOverflowException`, which zerolib lacks and bflat then fails codegen on — use a constant-size `stackalloc byte[N]` and cast the pointer instead; (2) larger structs/buffers make the compiler emit `memset`/`memcpy`/`memmove`/`memcmp`, so the shim now provides those; (3) no `new string(...)` / `ToString()` / string concat — build text into `stackalloc char[]` and draw with `Graphics.DrawChars`. Full GC/CoreCLR is the remaining Layer-4 "Menengah" work.

## Scheduler preemption (important)

**Ring-3 code is always preemptible; kernel code is not.** The timer handler passes `from_user` (interrupted CS RPL == 3) to `task::preempt`, which switches tasks only for ring-3 code — or for kernel code while the kernel-preemption flag is on, which only `scheduler_demo` (v0.2) does and turns back off immediately. Kernel tasks (dahan services, aio worker, the desktop) stay cooperative via `task::yield_now`. Do not enable *kernel* preemption globally: switching tasks in the middle of the boot task's heavy heap/framebuffer work corrupted memory (a race between `context_switch`, cross-task `without_interrupts`, and the console/heap), which showed up as a rodata dump + a cascade of exceptions. Preempting ring-3 code is safe because a timer that lands in user code holds no kernel lock by construction (syscalls run with IF cleared). A consequence: a kernel task that busy-loops without yielding starves everyone once it gets the CPU — long-running kernel tasks must yield.

After the boot demos, `desktop_loop` is the final loop: it yields to runnable user processes (`task::user_work_pending`) instead of `hlt`-ing, drains the keyboard queue into the terminal **unless the focused window belongs to a live process** (then keys stay queued for that process's `KEY_READ`), polls the PS/2 mouse into the window manager, and launches Start-menu/icon requests as separate processes (`app::spawn_named`). The framebuffer console and the compositor share the hardware framebuffer; once the desktop renders it covers the boot text, and the full boot log always remains on serial.

## Multi-process ring 3 (multi-process increment 1)

Several ring-3 programs run at once, preemptively, each in its own address space — verified headlessly by `multiproc_demo` → `MILESTONE: MULTIPROC OK` (IDE-only: `MPROC.ELF` lives on `/disk`).

- **Address spaces (`aspace.rs`):** every program links at the same addresses (image 0x40_0000, mmap arena 0x2000_0000, stack 0x7000_0000), all below `USER_ADDR_MAX` = 2 GiB = exactly **two PDPT entries under PML4[0]**. A process owns two private page directories; switching processes rewrites those two PDPT entries in the one shared hierarchy + flushes the TLB. Kernel mappings are shared by construction (no per-process copies to keep in sync). Space id 0 = kernel; a process's **pid is its space id**. Base-PD entries without the USER bit (kernel-owned) are shared into new spaces; entries a previous user program created are not. The mmap arena is per space (`memory.rs` `ARENAS`). **Frames are reclaimed:** `aspace::destroy(space)` frees every user page, every page table under the two directories and the directories themselves (skipping directory entries shared from the base — equal to the base entry or lacking USER — i.e. the bootloader identity maps at 0x0 and 0x1200000); `MUNMAP`/`unmap_user_pages` return frames too. The frame allocator keeps an intrusive free list (next pointer stored in the free frame; sentinel `u64::MAX`, since phys 0 can be usable) and `memory::frame_stats()` counts allocated/freed. `multiproc_demo` requires 0 frames leaked by its processes and 0 growth over 20 spawn/exit cycles. Destroy only a space that is not installed and whose tasks are all finished.
- **Per-task CPU state (`task.rs`):** each task carries its SYSCALL kernel stack top (also loaded into **TSS rsp0** — every ring-3 process/thread takes syscalls *and* ring-3 interrupts on its own 64 KiB stack), its longjmp context, user-rsp scratch, user-active flag, an **FXSAVE area** (`fxsave64`/`fxrstor64` on every switch — the kernel is soft-float, only ring-3 dirties SSE), and its address space. `switch_with` saves/loads all of them.
- **Launching (`app.rs`):** every program is a process (`task::spawn_process` → `process_body` → `enter_user_thread`; on exit `process_exited` detaches from + destroys the space). `spawn_named`/`spawn_with_args` return the pid (desktop, shell `run`, PROC_SPAWN); `run_named` = spawn + `app::wait` (Blocked on `process::wait_key`, woken at exit) — the boot demos use it to keep their order. There is no longer a synchronous "attached" mode where an app ran on the launcher's own task (sharing the boot task's privilege stack, unkillable). `kill(pid)` finishes all tasks of the space. `process.rs` holds the registry (args, exit codes).
- **Fault containment (`interrupts.rs`):** a #PF/#GP from ring 3 prints rip/rsp and calls `usermode::exit_user(FAULT_EXIT_CODE = 0xDEAD)` — it ends that program (thread) like an EXIT instead of panicking the OS.
- **Keyboard focus:** windows record their creator (`Window.owner`); `wm::focus_owner()` = owner of the topmost non-minimized window. `KEY_READ` returns keys only to the focus owner (when the terminal has focus they stay with the terminal); others get 0, and an empty `KEY_READ` yields the CPU.
- **CPU accounting** charges the *running task's* process (`task::current_space_id_irq`), not the installed space — the launcher installs a new program's space while loading its ELF, and that time is not the program's (charging the installed space made the multiproc test pass without preemption; caught by its negative control).
- **The self-test has a negative control:** it requires `task::user_preemptions()` (timer switches away from ring-3 code) to grow by ≥ 10 while two non-yielding copies run. With ring-3 preemption disabled it reports `preemptions=0, concurrent=false` and FAILS — keep it that way when changing the scheduler.

**Kernel gotcha (root cause of a recurring Heisenbug): static kernel stacks must be 16-byte aligned.** `gdt.rs` declared `DOUBLE_FAULT_STACK`/`PRIVILEGE_STACK` as bare `[u8; N]` — alignment **1** — so the linker could put them at any byte. In one layout the privilege stack sat at `…4b1`, making `SYSCALL_KSTACK_TOP` and TSS rsp0 odd: every ring-3 syscall then ran on a stack violating the x86-64 16-byte ABI alignment, and the boot died at HELLO.ELF's first syscall with the classic rodata-dump cascade. Whether the address happened to be aligned depended on unrelated code (adding a mouse clamp flipped it), which is exactly the "re-triggers whenever a change shifts the layout" behavior recorded for earlier crashes below — some of those were very likely this. **Proven causally:** on a layout that boots, forcing the top 15 bytes lower reproduces the identical crash signature; aligning fixes it. Stacks are now wrapped in `#[repr(C, align(16))] struct Stack<const N>`. Heap-allocated task stacks were already fine (`prepare_stack` / `spawn_ring3` round the top down with `& !0xF`). Also: TSS rsp0 is written with `write_unaligned` because `TaskStateSegment` is `packed(4)` (rsp0 at offset 4) — a `write_volatile` through that misaligned pointer is UB; it is not what caused the crash (an earlier note claimed so — wrong; that change merely shifted the layout).

**Frame allocator:** `BootInfoFrameAllocator` keeps a cursor (region index + next address). It used to call `usable_frames().nth(next)` — re-walking the memory map from the start for every frame, O(frames handed out) per allocation — which made every ELF load slower as boot progressed. The cursor cut boot-to-READY from ~35 s to ~20 s (tick estimate; ~83 s → ~52 s wall on IDE).

**Source layout — HAL boundary (multi-arch M0, increments 1–3, 2026-11-01):** x86 CPU code lives in `kernel/bzkernel/src/arch/x86/` (`gdt`, `interrupts`, `usermode`, `smp`, `vmx`, `context`, `paging`, `aspace`) and PC port-I/O devices in `src/platform/pc/` (`serial`, `ata`, `mouse`, `pci`, `rtc`, `power`, `audio`); `main.rs` re-exports them at the crate root (`pub(crate) use arch::x86::{…}`), so `crate::gdt`, `crate::serial`, etc. still resolve. The kernel heap is now mapped NX. The context switch is behind `crate::arch::context` (`FpuState`, `prepare_stack`, `switch` — `arch/x86/context.rs` holds the FXSAVE/FXRSTOR and stack-switch asm), so `task.rs` (the scheduler) is architecture-neutral. New hardware code goes under `arch/` or `platform/`. (Name the arch module `x86`, not `x86_64`: a module named like the `x86_64` crate makes paths ambiguous.)

**Boot protocol HAL + Device Tree (multi-arch M1, increment 1, 2026-11-01):** the kernel no longer sees the `bootloader` crate. `arch/x86/boot.rs` holds the entry point (`entry_point!` + `BOOTLOADER_CONFIG`) and converts the crate's hand-off into the protocol-neutral **`boot::BootInfo`** (`boot.rs`: loader name, physical-memory offset, a fixed 512-entry memory map of `MemRegion { start, end, usable }` merged on insert — filled before the heap exists, `boot::Framebuffer` with `boot::PixelFormat`, and `Firmware { rsdp, dtb }`), then calls `kernel_main(&'static boot::BootInfo)`; `boot::info()` returns it anywhere. `memory::BootInfoFrameAllocator` takes `&[MemRegion]`, `framebuffer.rs` wraps the mapping in its own `FrameBuffer`, FB_INFO maps `boot::PixelFormat`. `scripts/check-arch-boundary.sh` now also forbids `bootloader_api` in generic files. **Syscalls run with interrupts ON; files without the BKL (2026-11-01):** `usermode::syscall_dispatch_c` enables interrupts for the body of every syscall and disables them again before `kernel_exit` + the `sysret` path (after `pop rsp` the stack is the user's — an interrupt there would push onto it). This is safe because kernel code is never preempted (a timer in ring 0 does not switch tasks) and every lock an interrupt handler also takes is taken with interrupts off (keyboard queue, serial/console, scheduler `try_lock`). **Parallel threads within one process (2026-11-01):** threads of one process now run on several CPUs at once (`task::PARALLEL_THREADS`, default on; `set_parallel_threads(false)` / shell `cpu threads-off` restores "at most one thread of a process on a CPU", the `busy_spaces` rule). This needed an **SMP-safe ring-3 runtime** in `bzstart.rs`: the bump allocator (`SystemNative_Malloc`, behind `new`/arrays) is one critical section under `HEAP_LOCK` (spin, YIELD after 64 rounds); **`bz_mutex_lock` was not atomic** (`if *m == 0 { *m = 1 }` — two CPUs could both take it) and now uses a CAS; the mutex demo's slot claim and the thread demo's counter use atomics; new shim exports `bz_atomic_add` / `bz_atomic_add32` / `bz_atomic_cas32` (zerolib has no `Interlocked`) — **any C# code sharing memory between threads must use these or `BzMutex`**; `thread.cs` and `bcl2.cs`'s task worker were fixed accordingly (they relied on threads never running simultaneously). Verified by `pthread.cs` → `PTHREAD.ELF` (3 workers allocate `new int[16]` in a tight loop, stamp + keep 480 arrays each and verify them at the end, count work with atomic adds) and `smp_threads_demo` → `MILESTONE: SMP THREADS OK`: exit 0 and the scheduler-recorded peak (`task::watch_space` / `watched_peak` — measured on every switch on every CPU; sampling from the boot task undercounts, since the sampler itself occupies a CPU) = 2 threads on 2 CPUs, 4 on 4. Negative controls: with `HEAP_LOCK` disabled PTHREAD reports overlapping allocations ("HEAP RUSAK", exit 1); with `PARALLEL_THREADS=false` the peak is 1 and the test fails.

**I/O APIC (2026-11-01):** device IRQs no longer come through the 8259. `arch/x86/ioapic.rs` reads the I/O APIC and the ISA interrupt-source overrides from the MADT (QEMU: PIT IRQ 0 → GSI 2), programs one redirection entry per line the kernel uses with the **same vectors the PIC used** (32 + irq, so the IDT handlers are unchanged), masks the 8259 completely, and from then on `interrupts::end_of_interrupt` acknowledges the **Local APIC** (`ioapic::active()`; the PIC spurious stubs send no EOI). Routing: **PIT → CPU 0** (the scheduler charges PIT ticks to CPU 0's task and boot timing relies on it), **keyboard + mouse → the last CPU** (their handlers only touch the keyboard queue's spin lock and the mouse atomics). `ioapic::init` runs right after `smp::init` (needs the MADT, the LAPIC mapping and the AP LAPIC ids — `smp::lapic_id_of`, `cpus_online`, `map_mmio`). `ioapic::self_test` proves the routes without a human: the 8042's commands **0xD2 / 0xD3** put a byte in its output buffer as if the keyboard / mouse had sent it, raising a real IRQ 1 / IRQ 12 — a key-release code (0x9E, no character) and one empty mouse packet — and per-CPU counters (`ioapic::note_irq`, shown by `cpu`) must show them on the routed CPU → `MILESTONE: IOAPIC OK` (in the smoke list for every medium; with one CPU everything routes to CPU 0). This also makes UEFI boots independent of the firmware's 8259 masks.

**SMP increment 5 — fine-grained locking (2026-11-01):** syscalls whose handlers touch only state behind its own lock run **without the BKL** (`syscall::bkl_free`): MMAP/MPROTECT/MUNMAP (paging context `memory::CTX` → `ARENAS`, always in that order), YIELD/THREAD_SELF/FUTEX_WAIT/FUTEX_WAKE (scheduler lock; `task::futex_wait_if` compares the user word and blocks in one step under it, so no wake-up is lost), DEBUG_WRITE (serial + console locks), ABI_VERSION, IS_INTERACTIVE; and (increment 5b) the **window system** — WIN_CREATE/WIN_CMD/WIN_PRESENT/FB_INFO take `wm::WM`, then theme/wallpaper/RTC/process-registry locks *inside* it (never the reverse), KEY_READ = keyboard queue + `wm::WM` — the **process registry** (PROC_LIST, PROC_ARGS, SYS_STAT: `process::APPS`, scheduler, heap lock) and CLOCK_RTC (the CMOS index/data port pair got its own `CMOS_LOCK` in rtc.rs — the tray clock is read during every compose, so two CPUs composing at once would read each other's registers). PROC_WAIT stayed under the BKL here (its alive-check and block must be one step against the child's exit wake-up) — later moved out via `task::block_while`. Everything else still takes the BKL. Rules learned here: **(1)** "servicing a ring-3 syscall" (which enables pointer validation) is **per-task** state (`task::set_in_user_syscall`, mirrored per CPU and saved/restored on switch) — it was a global flag, so a kernel-internal `dispatch` on one CPU could have switched off validation of another CPU's user pointers (a syscall can also yield and resume elsewhere); **(2)** **never TLB-shootdown while holding a lock**: another CPU may spin on that lock with IF off and never ack — `memory::unmap_user_pages` now only unmaps and returns the frames, `release_frames` shoots down with no lock held and *then* frees them (freeing first would let a CPU reach a recycled frame); `user_mprotect` shoots down after releasing `CTX`; **(3)** the shootdown waits with interrupts **enabled** (two concurrent shootdowns must ack each other). `syscall::set_fine_locking(false)` restores the all-BKL behavior. Verified by `smp_finelock_demo` (two workloads, `smp_finelock_run`; `smpgui.cs` → `SMPGUI.ELF` = fill + blit into its own window, SYS_STAT, PROC_LIST per round, one present at the end: ×1.41 with 2 CPUs, BKL waits ~1500 → 3; **the WM lock is now split**: a compose took ~1.5 s in TCG while holding `WM`, so each window's pixels got their own lock (`wm::SharedCanvas` = `Arc<spin::Mutex<AppCanvas>>`); `WM` guards only the structure — `draw_on_window`/`blit_on_window` look the canvas up under `WM`, **drop `WM`**, then lock only that canvas; `compose_into` **clones the `Wm` structure** under `WM` (cheap: canvases are shared `Arc`s; `Window`/`Wm` derive `Clone`) and composes the snapshot without `WM`, locking one canvas at a time. Never take `WM` while holding a canvas lock. `wm::draws_during_compose()` counts draws that overlapped another CPU's compose (≈1,000 in the boot test, required > 0); SMPGUI now presents every 64 rounds and runs ×5.1 (2 CPUs) / ×3.3 (4 CPUs) vs all-BKL; the first version of the test presented every 16 rounds and measured a meaningless ×145 because one compose under the BKL froze every other CPU; and `smpsys.cs` → `SMPSYS.ELF`: one copy per CPU loops mmap → stamp → mprotect RO → verify → munmap → THREAD_SELF for ~1.5 s, run once all-BKL and once fine-grained) → `MILESTONE: SMP FINELOCK OK`: pages intact in both runs, BKL-free syscalls in the kernel on several CPUs at once (peak = CPU count), BKL waits ~7000 → ~5, throughput ×1.4 with `-smp 2` and ×2.25 with `-smp 4`; negative control (fine path off) fails with 0 BKL-free syscalls. Next candidates for their own locks: the window manager (WIN_* / KEY_READ — the busiest syscalls of the GUI apps), VFS/FAT, process registry.

**SMP increment 4 — symmetric SMP kernel with a Big Kernel Lock (2026-11-01):** every CPU runs the same scheduler (`task.rs`): one task list, a per-CPU `current`, each CPU picks its own next task round-robin; kernel tasks and ring-3 processes run on **any** CPU except pinned ones (task 0 = boot flow/desktop on CPU 0, one **idle task per CPU** incl. CPU 0 — so `futex_wait_block` always really blocks). **All kernel code holds the BKL** (a FIFO ticket lock): syscalls (`kernel_enter`/`kernel_exit` in `usermode::syscall_dispatch_c`, served on the CPU that issued them), kernel tasks, ring-3 fault handling (`kernel_enter` in #PF/#GP). It is dropped when entering ring 3 (`enter_user*` call `kernel_exit`), in `task::idle_halt()` (the desktop loop's `hlt` — **never `hlt` while holding the BKL**, it stalls every other CPU's syscalls), and around every context switch: "holds the BKL" is per-task state (`Task.bkl`, mirrored in per-CPU `CPU_BKL`) restored after the switch (`resume_bkl`). So the kernel's single-core assumptions still hold, while syscalls and kernel tasks execute on all cores. Rules: **(1)** the BKL is waited for with interrupts *enabled* (a CPU queued on it must still ack TLB-shootdown IPIs); **(2)** never wait for the BKL while holding the scheduler lock (`switch_with` drops the BKL first); **(3)** interrupt handlers run without the BKL — data they share with kernel code needs its own spin lock/atomics (keyboard queue, mouse, ticks, scheduler: all already are); **(4)** a task is `running` from pick until its context is saved — the next context clears it in `finish_switch` (per-CPU `PREV`), so no CPU resumes a half-saved task; **(5)** `tasks` is `Vec<Box<Task>>`; **(6)** threads of one process never run simultaneously (`busy_spaces`; the ring-3 runtime is not SMP-safe); **(7)** a dead process's space is freed only after no other CPU runs its threads (`app::destroy_when_home` → `task::wait_space_stopped`, which yields so a CPU queued on the BKL can finish; a killed task leaves at its next timer tick or in `kernel_exit`). Per-CPU plumbing: one SYSCALL stub per CPU incl. the BSP (`syscall_entry_<n>`, slot n of `CPU_USER_RSP`/`CPU_KSTACK`; table of **relative** offsets — the kernel is PIE), per-CPU page-table roots (`aspace::install` installs on the calling CPU; AP roots re-copy the master's kernel half), per-CPU TSS rsp0; the longjmp context and user-active flag live in the **task** (`current_kctx_ptr`), not in globals. `paging::map/unmap/protect/is_mapped` use **the active CPU's root for user addresses** (< 2 GiB) and the master `PageMap` for kernel addresses — the stored mapper reaches the wrong process on an AP. `smp::wake_others()` pings idle CPUs when a task becomes runnable. Verified: `MILESTONE: SMP KERNEL OK` (`smp_kernel_demo`: 6 kernel tasks doing heap work between yields ran on every CPU — mask 0b1111 with `-smp 4` — and syscalls were served on the APs) plus `SMP SCHED OK` (ring-3 copies in parallel, exact SSE sums, kill, 0 leaks); negative control: `AP_ENABLED=false` fails both. `cpu` shows per-CPU syscalls / kernel-task switches / ring-3 ticks / BKL waits / migrations. **Boot-time note:** wall-clock to READY is unchanged (~54 s with 2 CPUs vs ~51 s with 1), but the *tick estimate* jumped (~44 s vs ~21 s) because the BSP now spends far less time with interrupts off — compare wall-clock (`tstamp`-style serial timestamps), not the tick estimate, across CPU counts. Next: fine-grained locks to shrink the BKL (scheduler is already separate), an SMP-safe ring-3 runtime (parallel threads), IOAPIC IRQ routing.

**SMP increments 1–2 (`arch/x86/smp.rs`, 2026-11-01):** CPUs come from the ACPI MADT (`power::find_table(b"APIC")`). APs are started with INIT-SIPI-SIPI through a trampoline (16-bit → 32-bit → 64-bit, AT&T `global_asm!`) copied to physical **0x8000**; its slots (`ap_cr3`/`ap_stack`/`ap_entry`/`ap_arg`) are patched per AP. CR3 at the moment paging turns on is a **temporary PML4** whose path to 0x8000 is cloned with an identity mapping — the shared tables are never modified. `ap_main` switches to the kernel CR3, then (**increment 2**) takes its **own GDT + TSS** (`gdt::load_on_ap`: same selector layout as the BSP — asserted — with private double-fault IST and rsp0 stacks, heap-allocated and leaked; a TSS descriptor goes busy when loaded, so one per CPU), loads the shared IDT (`interrupts::load_on_ap`), starts a periodic **LAPIC timer** (100 Hz, vector 0xF0; the BSP calibrates the LAPIC timer against 3 PIT ticks before starting APs) and idles in `enable_and_hlt`. IPIs: vector 0xF1 ping, 0xF2 **TLB shootdown** (`smp::tlb_shootdown()` broadcasts all-but-self and waits for every online CPU's ack), 0xFF spurious (no EOI). Per-CPU state is `smp::CPUS[MAX_CPUS=16]` (BSP = #0, APs in MADT order), and `smp::cpu_index()` / `arch::cpu::id()` find the current CPU **by its LAPIC id** — not GS: without `swapgs` on every ring-3 entry, user code can reload GS, so the GS fast path waits for the per-CPU SYSCALL entry. `smp::self_test()` → `MILESTONE: SMP PERCPU OK` (each AP computed its own index, timer ≥ 5 ticks in 110–165 ms, directed ping acked, two shootdowns acked; negative control: with the AP timer off it fails with 0 ticks). Shell `cpu` shows per-CPU timer/IPI/TLB counters. The frame allocator never hands out memory below 1 MiB (`LOW_MEMORY_END`) so 0x8000 stays free, and `smp::init` refuses if 0x8000 is not usable RAM. The scheduler is still single-core on purpose — before tasks can run on APs: per-CPU SYSCALL state (GS/swapgs), per-CPU page-table roots (the PDPT-swap address spaces are single-core), real locks where `without_interrupts` stands in for one, and calling `tlb_shootdown` wherever a mapping shared with other cores changes. `MILESTONE: SMP OK` + `SMP PERCPU OK` (smoke: AHCI and UEFI boot with `-smp 2` and require both).

**UEFI boot gotcha (was broken, unnoticed):** `pic8259::initialize()` *restores the IRQ masks the firmware left*. Legacy BIOS leaves the 8259 open; UEFI firmware (OVMF) masks it fully (`0xff`/`0xff`) because it uses the LAPIC timer — so on UEFI no PIT tick ever arrived and boot hung in `scheduler_demo` (`ticks=0`). `interrupts::init` now explicitly unmasks timer/keyboard/cascade/mouse (and logs the firmware masks), and `smp::enable_bsp_lapic` puts the BSP LAPIC in virtual-wire mode (LINT0 = ExtINT) early. The smoke tests now also boot the UEFI image (when OVMF is downloaded under `kernel/target/ovmf`).

**Spawn/argv/wait (2026-11-01):** syscalls `PROC_SPAWN`=40 (path = app name or VFS path, args string), `PROC_WAIT`=41, `PROC_ARGS`=42 (`COUNT` = 43). A wait sleeps in the scheduler's `Blocked` state on futex key `process::wait_key(pid)` (= `0xB2 << 48 | pid`, above every user address) and `process::app_exit` wakes it — no busy loop; the alive-check and the block are one step under the scheduler lock (`task::block_while`, see the BKL-free processes note above). Args live in the process registry (`process::set_args` right after spawn; the child cannot run before the spawner returns). Strings are capped at 255 bytes by `read_user_path_checked`. `BzProcess.Start/WaitForExit/GetArgs` in `bzbcl2.cs`; shell `run <app> <args>`; verified by `proctest.cs` (`MILESTONE: PROCCTL OK`). FAT scans (`free_space`, cluster allocation) read each FAT sector once (`scan_fat`) — reading one sector per cluster added ~8 s of boot.

**Process control (increment 2):** closing a process's last window ends it (`wm` records `closed_owners`; `desktop_loop` → `app::reap_closed_windows` kills detached owners with no window left — an interactive app would otherwise keep polling invisibly); shell `ps` lists kernel tasks + apps and `kill <pid>` stops a spawned process; an empty `KEY_READ` **yields** for spawned processes (own kernel stack) so polling loops don't burn their slice. Mouse position is clamped to the screen (`mouse::set_bounds`) — it used to accumulate past the edges, leaving a dead zone as wide as the overshoot. All verified by `multiproc_demo` (`ps lists spawned / close-last-window ends process / shell kill`) and live in QEMU via monitor `sendkey`/`mouse_move` (scratch scripts drive the desktop and `screendump`).

Still missing (next increments): process teardown (EXIT/PROC_KILL) and thread create/join still take the BKL; no per-process handle tables or signals.

## Ring-3 page-table gotcha (do not regress)

To execute a user page, **every** level of the page-table walk must have `USER_ACCESSIBLE` set (permission is the AND of all levels) **and** must not have `NX` set (an instruction fetch faults if NX appears at any level). Upper tables are shared with kernel mappings that lack USER, and the bootloader's low PML4 entry has NX set. `memory::make_user_path` ORs in USER and clears NX on the intermediate entries along the path to each user page, then flushes the TLB. `elf::load` and `memory::map_user_region` both call it. Leaves keep their own bits, so kernel memory stays protected. `requirements.md` (in Indonesian) is the authoritative spec; its §17 checklist tracks progress and must be updated (with honest annotations) when items land.

## Hard-won Build Gotchas

- **Never build `bzkernel` for the host.** It is deliberately excluded from workspace `default-members`; building it without `--target x86_64-unknown-none` hits an LLVM error ("offset is not a multiple of 16", x86-interrupt ABI on MSVC). `cargo build` at `kernel/` root builds `abi` + `bzimage`, and `bzimage` pulls the kernel in as an artifact dependency with the right target (requires nightly + `bindeps`, pinned via `rust-toolchain.toml` / `.cargo/config.toml`).
- QEMU on this machine lives at `C:\Program Files\qemu\` (not on PATH); `bzimage` and the scripts auto-detect it, override with the `QEMU` env var. `QEMU_EXTRA="-s -S"` adds GDB debugging.
- OVMF firmware for UEFI runs is auto-downloaded by `ovmf-prebuilt` into `kernel/target/ovmf/`.
- Keep kernel console output ASCII-only: the framebuffer font covers basic latin, and serial logs read cleanly.
- The GDT must reload SS/DS/ES after `CS::set_reg` (stale bootloader selectors #GP on the first interrupt) — don't "simplify" that away.

## ABI Contract (critical invariant)

`kernel/abi` (`bz-abi`) is the single source of truth for the Rust↔C# boundary; `runtime/Buitenzorg.Runtime/Sys/` mirrors it. Any ABI change must touch **both sides + both contract test suites (`cargo test -p bz-abi`, `AbiContractTests.cs`) + `docs/abi.md`** in the same change. Syscall numbers are append-only. `Buitenzorg.Runtime` must stay NativeAOT-compatible (no dynamic reflection; JSON via source-generated context).

## What Buitenzorg Is

A hybrid, AI-native operating system:

- **Rust** (`no_std`) for the "unsafe world": bootloader (UEFI + legacy), kernel (ring 0), memory manager, scheduler, interrupts, and hardware drivers (NVMe/SATA/IDE/USB storage, GPU, input, network, audio).
- **C#/.NET** for the "managed world" (ring 3): system services, compositor/window manager, desktop environment, AI subsystem, SDK, and apps. Runtime strategy: NativeAOT first, CoreCLR/JIT later, hybrid long-term.
- **AI-native**: local LLM engine, computer vision, and GenAI (image/audio/video) are OS-level services (Layer 6) with a Hugging Face-integrated Model Manager — not add-on apps.
- **Polyglot app model**: one manifest/app model, four app variants (console, desktop, web, widget), writable in C#, JS, TypeScript, or Python.
- Unlike Cosmos (C# kernel via IL2CPU), Buitenzorg keeps the kernel in Rust and gives C# the full .NET runtime in user-space.

## Architecture (10 layers, bottom-up)

Hardware (x86-64 → ARM64 → RISC-V) → Bootloader (Rust) → Kernel (Rust) → Driver subsystem (Rust, some C# user-space) → Managed runtime (.NET, the critical Rust↔C# bridge) → System services (C#) → AI subsystem (C#) → Desktop environment (C#) → App framework/SDK (polyglot) → Applications.

**Interop rules (Layer 4 is the make-or-break layer):**
1. All cross-language calls go through the C ABI (`extern "C"` + P/Invoke/syscall).
2. Only primitives, pointers, and `#[repr(C)]` structs cross the boundary.
3. Syscalls form a stable numbered table (Linux-style).
4. Large data (framebuffers, files, AI tensors) uses zero-copy shared memory, never marshalled copies.
5. Managed objects are GC-pinned while their pointers are held by Rust.

## Roadmap Order

Versions are codenamed after plant growth stages (homage to Bogor Botanical Gardens). The dependency order matters:

1. **v0.1–0.4** — bootloader → kernel core → drivers/boot media → managed runtime bring-up ("Hello from C#")
2. **v0.5–0.7** — VFS/services/async I/O → graphics/window system → desktop environment + terminal
3. **v0.8–0.10** — app framework + VS Code tooling (DAP debugging, debug bridge) → web/widget apps → theme engine (8 built-in themes) + package manager
4. **v0.11 GPU acceleration must land before v0.12 AI subsystem** (AI depends on the compute API; CPU fallback required)
5. **v0.13–0.16** — virtualization → polyglot runtimes → **v0.15 "Matang" managed runtime C# lengkap (GC + full .NET BCL: LINQ/Regex/Tasks/…) — prasyarat** → v0.16 preloaded suite + optimization pass
6. **v1.0** — stable x86-64 release; **v1.x** — ARM64, then RISC-V ports

`requirements.md` §17 is the development checklist — mark items `[x]` there as they are completed.

## Design Principles to Uphold

- Microkernel-leaning: drivers/services in user-space where possible, so crashes are isolated.
- Performance is policy, not afterthought: async io_uring-style I/O, zero-copy paths, parallel dependency-aware init, benchmark regression checks in CI.
- HAL is multi-arch from day one (x86-64 first, but don't hardcode against ARM64/RISC-V portability).
- Offline-first AI with per-app permission broker (camera/mic/model access).
- Theme engine is token-based (design tokens, hot-reload, `.theme` packages, dark/light variants).
